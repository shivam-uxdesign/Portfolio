01 — Overview

Rupyy powers the end-to-end auto-loan journey for lenders, operations teams, and field agents. After ten years of independent growth, its products shared a workflow — but not a foundation.

The ecosystem had grown into four distinct platforms — loan origination, payments, lead tracking, and title processing — each evolving its own interface conventions.

What held them together was a thin UI kit that couldn't scale with the number or complexity of products being built. I owned the system end-to-end: the foundations, the component architecture, and the documentation that made it adoptable — partnering closely with engineering to ensure it reached production.

One foundation Four products Minimal customization
02 — The Problem

Without shared definitions, every team rebuilt the same thing.

As Rupyy's products scaled, the absence of a system stopped being a design inconvenience and became a delivery bottleneck. Building the new Admin Portal made it impossible to ignore.

› FRAGMENTATION

Four products, four dialects

A decade of independent evolution left each platform with its own buttons, forms, and interaction rules — and no agreement on which was correct.

› DUPLICATION

The same patterns, rebuilt repeatedly

Teams re-solved solved problems. Components were copied, tweaked, and forked, multiplying maintenance instead of sharing it.

› DESIGN DEBT

Compounding inconsistency

Every new screen widened the gap between products, eroding trust in the interface and the data behind it.

› MISALIGNMENT

Design and engineering out of sync

With no shared source of truth, handoff meant interpretation. Rework, ambiguity, and friction were built into the process.

04 — Strategy

Design the system as infrastructure, not a component library.

If the gap was definitions, the system had to lead with them. Three principles set the direction before a single component was drawn.

01

Constraints over choices

A small set of correct defaults — tokens, scales, states — so the right decision is the easy one and drift has nowhere to start.

02

Composable, not bespoke

Flexible primitives that assemble into patterns and drop into any product with minimal customization.

03

Handoff is part of the system

Adoption is designed in from day one — documentation and dev parity treated as features, not afterthoughts.

Goals & success signals
G1

Consistency — one visual and behavioural language across all four products.

G2

Velocity — teams compose screens instead of rebuilding primitives.

G3

Less rework — design and engineering work from a single source of truth.

G4

Accessibility by default — WCAG-aligned contrast and states baked into tokens.

Stakeholder alignment

Because the system would reshape how four product teams worked, buy-in had to come before the build.

I aligned product and engineering leads on a shared definition of "done," then anchored the first release to the Admin Portal — a live product that proved the system in real delivery, not in isolation.

07 — Adoption & Rollout

Three sources of truth, one connected handoff.

A system only succeeds if it reaches production. I treated handoff as part of the system — connecting design intent, live behaviour, and documentation so engineers never had to guess.

F

Figma Dev Mode

Design intent

Spacing, tokens, states, and behaviour annotated directly in the design files — specs read straight from the source.

S

Storybook

Live components

The source of truth for built components — engineers validate behaviour, props, and states against the real thing.

C

Coda Docs

The connective tissue

Connects design intent to implementation — usage guidelines, do/don't rules, and QA checks in one referenceable place.

Migration approach

Rather than a risky big-bang rewrite, the system landed where it could prove itself — the Admin Portal first.

Step 01

Anchor in a real product

Shipped the Admin Portal on the system so adoption was validated in live delivery, not a sandbox.

Step 02

Onboard the teams

Walkthroughs of tokens, components, and the contribution path, with docs as the always-on reference.

Step 03

Migrate incrementally

Adopt component-by-component across LoanBox, PaymentBox, LeadBox, and TitleBox — replacing forked patterns over time.

09 — Key Learnings

What building it from the ground up taught me.

This was the first design system I built end-to-end. It reshaped how I think about scale — and where the real work lives.

Challenges

The hard part wasn't the UI

  • Defining shared constraints across teams that had each made their own rules.
  • Earning adoption while products were still actively shipping.
  • Treating documentation as a product, not a deliverable.
Trade-offs

Deliberate constraints

  • Fewer options by design — flexibility was traded for consistency.
  • Anchoring to one product first slowed full coverage but de-risked adoption.
  • Composable primitives over polished one-offs.
What's next

Future opportunities

  • Token sync between Figma and code to close the last manual gap.
  • Usage analytics to see which components actually get adopted.
  • Maturing the contribution model into true federated ownership.
Reflection

Beyond components, the work was about structure, constraints, and documentation teams could rely on over time. It gave me a foundation in designing systems as infrastructure — and the confidence to evolve them in close partnership with engineering.
